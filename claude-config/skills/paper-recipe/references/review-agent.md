# 审稿代理: 交付前的固定一站

生成与审稿分离的核心依据在于二者的认知不对称性: **生成需要上下文, 审稿需要抽离上下文.**
生成端依赖当前会话所积累的详略尺度, 已核事实与链接表; 审稿端则恰恰相反 —— 创作者即便重读自身产出数遍亦难察瑕疵, 因其缺陷在作者的语境中已被认知同化. 审稿代理仅接收规则与待审草稿, 规则置于其上下文的最顶层; 审稿代理直接对照规则开展识别, 而非在内容生成的负载下被动回忆规则.

用户已授权 (2026-08-28): 本站的审稿代理属于固定流程, 无需逐次请示.

## 分工

生成端 (主会话) 仅需维持两项零边际成本的习惯, 其余核查全部交由审稿代理承担:

- 段落首句交代意图 (math-rules 第〇节)
- 符号首现即释 (math-rules 第一节)

## 代理设置

- 类型: 指定为 `zh-reviewer` (定义于 `~/.claude/agents/zh-reviewer.md`, 固定配置 `model: claude-opus-4-6`). 采用不同权重的模型进行审稿属于既定设计: 当生成端与审稿端模型权重相同时, 两者文体先验一致, 易共享盲区; Opus 4.6 具备不同的中文语感先验, 恰好填补规则清单未能覆盖的部分 (对应任务书中的"语感项"一节). **不要用 fork** —— fork 会继承主会话上下文并强制采用同款模型, 将从两端削弱审稿机制的独立价值.
- **必须走会话内 Agent 工具, 禁止 headless `claude -p`**: 用户环境中设有 ANTHROPIC_API_KEY, headless 调用会静默产生 API 计费; 会话内子代理则计入订阅额度. 用户已明确要求仅走订阅额度.
- 新建 agent 类型的注册表可能需至下一轮交互方能刷新; 若出现 "Agent type not found" 提示, 须等待一轮后再试, 禁止绕道通过 CLI 执行.
- 输入 (仅提供以下四项内容, 其余一概不予提供):
  1. stop-slop-zh 的 SKILL.md
  2. paper-recipe 的 math-rules.md
  3. delivery.md (链接与结构规则部分)
  4. 待审草稿
- 明确禁止: 解析或打开笔记中的 bookends 深链; 读取其他文件; 修改任何文件.
- **只许用 Read 工具, 禁用 Bash**: 后台代理无法响应权限交互提示, 一旦触发 Bash 权限拦截会导致代理进程静默终止, 且无法输出评审报告.
- **待审稿先拷贝到工作目录再交给代理**: vault 位于 iCloud 路径下, 不在授权目录范围内.

## 必交的五个产物

基于产物驱动的检查机制能强制实现全覆盖, 这是将检查从 grep 提升至语义层面的关键:

1. **逐公式符号对照表**: 公式 → 每个符号 → 解释它的原句; 缺失标注 [缺].
2. **逐段意图检查**: 每段用一句话概括其阐述的问题; 概括不出标注 [悬空].
3. **回译测试**: 抽取 8 个实质性句子, 提供英文回译与判定, 存在翻译腔之处给出修改方案.
4. **链接审计**: 检查是否存在对其他笔记的裸提及; 指向小节的引用是否使用标题级链接.
5. **分级 findings**: 划分为 严重 / 中等 / 轻微, 每条记录须给出 位置 + 规则依据 + 建议改法; 检验全部通过的项亦须明确注明"无发现".

要求从严: 宁可多报以待人工复核, 严禁漏报.

## 语体定稿 (审稿修订之后, 交付之前)

内容与语言分设两审: zh-reviewer 负责内容, 数学与链接规范; **语体定稿交给 Gemini 3.7 Flash** (由用户于 2026-08-28 确立, 其文风即为语体标准). 调用方式:

```bash
agy -p "$(/bin/cat 提示词文件)" --model gemini-3.7-flash-high > rewrite-gemini.md
```

提示词骨架: "重写成你自己会写的中文, 不给风格规则" + 硬约束清单 (公式, 推导与数值信息量不减; 深链保持原样且附着于原句; wiki 链接, 图嵌入, frontmatter, 标题行, 折叠块结构保持原样; 事实, 数据及结论不得改动或新增; 半角标点; 禁用工具, 直接输出全文).

**已知的坑**:
- agy 依赖用户的 Google AI Pro 订阅 (OAuth), 严禁改用 GEMINI_API_KEY (预付计费额度).
- 折叠块 (`> [!note]-`) 常被原样跳过, 需要单独抽离并单独执行一次后拼回.
- Gemini 会擅自拔高结论 ("验证通过"→"充分验证了有效性", "仍只有"→"严格控制在"), 定稿后必须通篇排查评价性副词与形容词, 越界之处均须改回. 注意 "充分小", "显著性" 这类数学术语不属于拔高, 切勿误改.
- Gemini 会删去解释性的转折与目的从句 —— 即交代"为什么要这样表述"与"这一步为后文做什么准备"的语句. 这些内容在模型视角下常被视作冗余, 却恰为读者理解所必需. 定稿后须逐段与原文比对, 凡遗失的说明性从句一律补回.
- 上述问题的更严重版本: **它会把重建推理的叙述整体改写成流程说明**, 顺手抹去原有的动机与障碍. 此现象关乎核心内容损耗而非单纯的语体差异, 参见 stop-slop-zh 第四节. 定稿后须逐段检查方法部分: 确认关键障碍是否仍在, 以及"为什么非得这样做"是否依然能够得到回答.
- 长篇文本应在 tmux 中执行, stdout 重定向至文件 (stderr 保留在面板中可见).

**定稿后核验清单** (逐项核验, 全部通过后方可覆盖 vault):
深链数不变且逐条格式完好; 标题行 diff 为空; 图嵌入 diff 为空; frontmatter diff 为空; 折叠块行数与结构保持一致; 数值集合对比无实质漂移 (允许 "四分之三"↔"75%" 等等价表述); 备份现行版后方可执行覆盖.

## 收尾

- 主会话依据 findings 进行修订; 对误报直接弃置, 无需向代理反馈.
- 修订幅度较大时可对改动部分再执行一轮复审 (可选).
- 代理与主会话即便引入异构先验, 亦仅能削减而非根除盲区共享. **它不替代用户终审**, 目标是将用户每轮终审所需拦截的错误类型压缩至一至两类.
- 成本量级: 单次运行消耗约三至五万 token, 约占单篇笔记总成本的一成.
